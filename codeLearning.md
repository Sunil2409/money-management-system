# Money Manager — Architectural Deep Dive for Mid-Level Python Developers

> **Purpose:** This document dissects the Money Manager codebase across four architectural layers, designed to prepare you for mid-level Python/Django interview questions. Read this not just to understand what the code _does_, but _why_ it was designed that way, what tradeoffs were made, and how you'd articulate these decisions to a senior engineer.

---

## Layer 1: The Data Layer

### 1.1 The Schema

This project has **two logical domains**: authentication and transactions. However, the data model uses **Django's built-in `User` model** for auth — there is no custom user model. The `accounts/models.py` file is empty. This is a deliberate simplification: Django's `contrib.auth.models.User` already provides `id`, `username`, `email`, `password` (hashed), `date_joined`, and all permission/group machinery. For an MVP-grade personal finance app, this is the right call — no premature abstraction.

The only custom model is `Transaction` in `transactions/models.py`. Here's the schema in relational terms:

```
Transaction
├── id          UUID (PK, default=uuid4, non-editable)
├── user_id     FK → auth_user.id (CASCADE delete, related_name='transactions')
├── amount      DECIMAL(12, 2)
├── category    VARCHAR(50) — choices from a predefined enum
├── status      VARCHAR(10) — 'spent' or 'credited'
├── description TEXT (blank=True, default='')
├── date        DATE
├── created_at  DATETIME (auto_now_add)
└── updated_at  DATETIME (auto_now)
```

**Indexes (3 composite):**
- `(user, -date)` — accelerates "show me my recent transactions" queries
- `(user, status)` — accelerates filtering by spent/credited
- `(user, category)` — accelerates category-based filtering

### 1.2 Key Design Decisions in the Data Layer

**UUID as primary key instead of auto-incrementing integer.**

_Why?_ Sequential integer IDs leak information — an attacker can guess `/api/transactions/42/` and probe other users' data. UUIDs prevent enumeration attacks. They're also essential if you ever shard the database across multiple nodes (no ID collisions). The tradeoff: UUIDs are 16 bytes vs 4–8 bytes for integers, and B-tree index performance is slightly worse due to random insertion order. For this application's scale, the security benefit outweighs the negligible performance cost.

**DecimalField for money, not FloatField.**

_This is non-negotiable for financial applications._ Floats are binary approximations — `0.1 + 0.2 != 0.3` in IEEE 754. Decimal maintains exact base-10 precision. `max_digits=12` means the number can have up to 12 total digits (e.g., `9,999,999,999.99` — just under 10 billion). This is the correct choice for a personal finance app.

**`on_delete=models.CASCADE` with `related_name='transactions'`.**

When a user is deleted, all their transactions are automatically deleted. The `related_name` lets you do `user.transactions.all()` — Django's ORM reverse-relationship sugar. Interview tip: know the difference between `CASCADE`, `PROTECT`, `SET_NULL`, and `SET_DEFAULT`, and when you'd use each.

**`blank=True` vs `null=True` on the description field.**

`blank=True` (Django form-level) allows the field to be empty in forms/serializers. The database column still stores an empty string `''`, not `NULL`. This avoids the classic SQL `NULL` comparison footgun (`NULL != NULL`). For text fields, empty string is almost always the right default over `NULL`.

**Database indexes via `Meta.indexes`.**

Not just `db_index=True` on individual columns — these are **composite indexes** covering the most common query patterns. The leading column is always `user` because every query is user-scoped. Index order matters: `(user, -date)` means queries filtering by `user` alone still use the index, but queries filtering by `date` alone won't.

### 1.3 Why No Custom User Model?

This is a common interview question. Django strongly recommends setting a custom user model _before_ the first migration. This project didn't, because:
1. The scope of user data is minimal (username, email, password).
2. Django's built-in `User` model is battle-tested and integrates with the admin, permissions, and SimpleJWT with zero extra code.
3. If the project needed user profiles (avatar, bio, currency preference), you'd create a `Profile` model with a `OneToOneField` to `User` — a pattern called the "profile pattern" that avoids migrating the user model later.

### 1.4 Migration Strategy

The `0001_initial.py` migration is the single initial migration generated by `makemigrations`. In production, migrations are applied automatically by the `entrypoint.sh` script via `python manage.py migrate --noinput`. The `--noinput` flag suppresses prompts, critical for non-interactive container startup. This is standard Docker-entrypoint pattern.

## Layer 2: Business Logic (Views/Services)

### 2.1 The Most Complex Function: `TransactionViewSet.summary()`

Let's walk through `summary()` line by line at the conceptual level. This is the aggregation endpoint that powers the dashboard's summary cards and doughnut chart.

**Cache Check (lines 1–6):**
```python
cache_key = f'summary_{request.user.id}'
cached_result = cache.get(cache_key)
if cached_result:
    return Response(cached_result)
```
The cache key is namespaced by user ID. Aggregation queries (SUM, COUNT) are expensive on large datasets — recomputing them on every dashboard load would hammer the database. A 5-minute TTL means the summary is at most 5 minutes stale. The tradeoff: users see slightly stale data, but the database stays responsive under load.

**Aggregation — Total Spent (lines 8–10):**
```python
total_spent = transactions.filter(status='spent').aggregate(
    total=Sum('amount')
)['total'] or Decimal('0.00')
```
`aggregate()` translates to `SELECT SUM(amount) FROM transactions WHERE user_id=? AND status='spent'`. The `or Decimal('0.00')` handles the `None` case — if a user has zero spent transactions, `Sum` returns `None`, and we normalize to `Decimal('0.00')`.

**Category Breakdown (lines 12–18):**
```python
category_data = (
    transactions
    .filter(status='spent')
    .values('category')
    .annotate(total=Sum('amount'), count=Count('id'))
    .order_by('-total')
)
```
This translates to:
```sql
SELECT category, SUM(amount) AS total, COUNT(id) AS count
FROM transactions
WHERE user_id=? AND status='spent'
GROUP BY category
ORDER BY total DESC;
```
`values('category')` triggers a `GROUP BY category`. `annotate()` adds computed columns. The result is a list of dicts like `[{'category': 'food', 'total': Decimal('150.00'), 'count': 3}, ...]`.

**Cache Write (line 26):**
```python
cache.set(cache_key, result, timeout=SUMMARY_CACHE_TTL)
```
The result is serialized and stored in Redis (or in-memory cache in dev). Since `Decimal` objects aren't JSON-serializable, they're converted to strings earlier (`str(total_spent)`). This is a practical concern — when the cache backend serializes to JSON, Decimal objects would raise `TypeError`.

**Cache Invalidation — the write-through pattern:**
Every `perform_create`, `perform_update`, and `perform_destroy` calls `cache.delete(f'summary_{request.user.id}')`. This is a **write-invalidation** strategy: rather than updating the cache on every write (complex, error-prone), we simply delete the cached summary. The next GET request will recompute and repopulate it. This is sometimes called "cache-aside with invalidation on write."

### 2.2 User-Scoped Queryset: The Security Linchpin

```python
def get_queryset(self):
    return (
        Transaction.objects
        .select_related('user')
        .filter(user=self.request.user)
        .order_by('-date', '-created_at')
    )
```

Every CRUD operation flows through `get_queryset()`. The `.filter(user=self.request.user)` is the **data isolation guarantee** — even if user A guesses user B's UUID, they'll get a 404 (not a 403) because the queryset is scoped before the lookup. `select_related('user')` performs a SQL JOIN to fetch the user in the same query, preventing the N+1 problem. Since we only need the user for the relationship (not for display), this is arguably unnecessary in the list view but is defensive against future code that might access `transaction.user`.

### 2.3 Authentication: CookieJWTAuthentication

The authentication class in `config/authentication.py` extends SimpleJWT's `JWTAuthentication` to support **httpOnly cookies**:

```python
class CookieJWTAuthentication(JWTAuthentication):
    def authenticate(self, request):
        access_token = request.COOKIES.get('access_token')
        if not access_token:
            # Fallback to Authorization header
            header = self.get_header(request)
            ...
        validated_token = self.get_validated_token(access_token)
        user = self.get_user(validated_token)
        return (user, validated_token)
```

**Why httpOnly cookies instead of localStorage?**

| Storage | XSS-vulnerable? | CSRF-vulnerable? | Automatic with requests? |
|---------|-----------------|------------------|--------------------------|
| localStorage | Yes (JS can read) | No | No (manual header) |
| httpOnly cookie | No (JS can't read) | Yes | Yes (browser sends) |

httpOnly cookies eliminate the XSS token-stealing attack vector entirely. A malicious injected script cannot `document.cookie` read the `access_token`. The tradeoff is CSRF vulnerability — but this project mitigates that with `SameSite=Strict` in production (cookies only sent on same-origin requests) and Django's built-in CSRF middleware.

### 2.4 The Frontend Token Refresh Pattern

`authFetch()` in `app.js` implements an **automatic token refresh interceptor**:

```
Request → Server returns 401 → refreshToken() → Server sets new cookie → Retry original request
```

This is client-side middleware. On 401, it calls `POST /api/auth/token/refresh/` with the `refresh_token` cookie, the server validates it, sets a new `access_token` cookie, and the original request is retried. If refresh fails, the user is logged out. This is the standard OAuth2 refresh token flow adapted for cookie-based JWT.

### 2.5 Error Handling & Logging

The custom exception handler (`config/exceptions.py`) wraps all DRF errors in a consistent envelope:
```json
{
    "error": {
        "code": "authentication_required",
        "message": "Authentication credentials were not provided."
    }
}
```

It maps HTTP status codes to human-readable error codes. It also logs 4xx as warnings and 5xx as errors with request context (method, path, user). This is production-grade observability — you can grep logs for patterns, set up alerts on error rates, etc.

**Logging architecture:** Each app has its own logger (`accounts`, `transactions`, `health`) configured separately in `logging_config.py`. The `LOG_LEVEL` is environment-controlled — `DEBUG` in dev, `INFO` in production. Key user actions (login, logout, transaction create/update/delete) are logged at `INFO` level with structured data.

### 2.6 Rate Limiting

Two tiers of throttling:
- **Login/Register:** 5 requests/minute per IP (`LoginRateThrottle`) — brute-force protection
- **General API:** 20/minute anonymous, 60/minute authenticated — abuse prevention

The `disable_throttle` fixture in `conftest.py` patches `SimpleRateThrottle.allow_request` to always return `True`, preventing rate-limiting from interfering with tests. This is tested correctly — the test suite uses `force_authenticate` which bypasses throttling anyway, but the fixture is a belts-and-suspenders approach.

## Layer 3: Routing & API

### 3.1 URL Architecture

The project uses a **two-level URL hierarchy**:

```
config/urls.py (root router)
├── admin/          → Django Admin
├── api/            → transactions/urls.py (DRF Router)
│   ├── transactions/              → GET (list), POST (create)
│   ├── transactions/{id}/         → GET, PUT, PATCH, DELETE
│   └── transactions/summary/      → GET (custom @action)
├── api/auth/       → accounts/urls.py (manual urlpatterns)
│   ├── register/                  → POST
│   ├── login/                     → POST
│   ├── token/refresh/             → POST
│   ├── logout/                    → POST
│   └── me/                        → GET
├── api/health/     → config/health.py (function-based view)
├── api/schema/     → OpenAPI 3.0 schema (auto-generated)
├── api/docs/       → Swagger UI
└── api/docs/redoc/ → ReDoc
```

### 3.2 DRF Router vs Manual URLs

Transactions use a `DefaultRouter` which auto-generates RESTful URLs from a `ModelViewSet`:
```python
router = DefaultRouter()
router.register(r'transactions', TransactionViewSet, basename='transaction')
```
This creates: `GET/POST /transactions/`, `GET/PUT/PATCH/DELETE /transactions/{id}/`.

Auth uses manual `urlpatterns` because the auth views are function-based (`@api_view`) and class-based views with custom `post()` overrides — they don't map cleanly to a ViewSet.

### 3.3 Serializers: The Data Boundary

Serializers are the **API contract** — they define what shape of JSON the API accepts and returns.

**TransactionSerializer:**
- `Meta.fields` explicitly lists which fields are exposed
- `read_only_fields = ['id', 'created_at', 'updated_at']` — the client can't set these
- `category_display` and `status_display` are read-only computed fields using `source='get_category_display'` — Django calls `get_FOO_display()` for choice fields, and the serializer exposes the human-readable label
- `validate_amount()` enforces `amount > 0` — a business rule at the API boundary

**RegisterSerializer:**
- `password = serializers.CharField(write_only=True)` — the password is accepted in the request but never serialized in the response
- `validate_email()` checks uniqueness — a second validation layer beyond the database unique constraint. The error message is user-friendly ("A user with this email already exists") rather than a raw IntegrityError
- `create()` uses `User.objects.create_user()` which hashes the password — never store plaintext passwords

### 3.4 Request/Response Lifecycle

Here's what happens when a user clicks "Save Transaction":

```
1. Browser: fetch('/api/transactions/', {method:'POST', body: JSON, credentials:'include'})
   └─ Browser automatically attaches access_token httpOnly cookie

2. Nginx: Receives request, proxies to backend:8000
   └─ Sets X-Forwarded-* headers

3. Django Middleware (in order):
   ├─ SecurityMiddleware — sets security headers
   ├─ SessionMiddleware — session handling
   ├─ CorsMiddleware — checks Origin against CORS_ALLOWED_ORIGINS
   ├─ CsrfViewMiddleware — CSRF token check
   ├─ AuthenticationMiddleware — attaches request.user
   └─ MessageMiddleware — flash messages

4. DRF: Request reaches TransactionViewSet
   ├─ CookieJWTAuthentication.authenticate()
   │   └─ Extracts access_token from cookies, validates JWT, returns (user, token)
   ├─ IsAuthenticated permission check passes
   ├─ Throttle check passes (< 60 req/min)
   └─ create() → perform_create(serializer)
       ├─ serializer.is_valid() → validate_amount() checks > 0
       ├─ serializer.save(user=request.user) → INSERT into DB
       └─ cache.delete(f'summary_{user.id}') → invalidate summary cache

5. Response: 201 Created with Transaction JSON
   └─ Nginx returns to browser
```

### 3.5 API Documentation (drf-spectacular)

The API is documented via OpenAPI 3.0 auto-generation. `SpectacularAPIView` introspects all views, serializers, and URL patterns to generate a schema at `/api/schema/`. Swagger UI at `/api/docs/` provides interactive documentation. The `SERVE_PERMISSIONS = [AllowAny]` and `SERVE_AUTHENTICATION = None` mean the docs are publicly accessible — acceptable for this project, but in a production internal API you might restrict this.

## Layer 4: Infrastructure & Deployment

### 4.1 Multi-Stage Docker Build

The `Dockerfile` uses a **builder pattern** — two `FROM` statements:

```
Stage 1 (builder):
  - Python 3.12-slim
  - Installs gcc + libpq-dev (compile-time deps for psycopg2)
  - pip install to /install prefix

Stage 2 (production):
  - Python 3.12-slim
  - Installs only libpq5 (runtime dep, no compiler)
  - COPY --from=builder /install → /usr/local
  - Creates non-root user (appuser)
  - Runs as appuser
```

**Why this matters:**
- The production image is smaller (no gcc, no headers — ~200MB vs ~500MB)
- No compiler on the production image reduces attack surface
- Non-root user is a container security best practice — if the app is compromised, the attacker doesn't get root on the container
- `HEALTHCHECK` uses the `/api/health/` endpoint — Docker monitors this and can restart unhealthy containers

### 4.2 Entrypoint Script

`entrypoint.sh` runs **before** the CMD (gunicorn). Its job:
1. **Wait for PostgreSQL** — a TCP socket check loop. Without this, Django would try to connect before Postgres is ready and crash. The 2-second retry loop is a simple but effective pattern.
2. **Run migrations** — `migrate --noinput` ensures the schema is up-to-date. In a multi-replica deployment, only one replica should run migrations (or you use a migration lock).
3. **Collect static files** — `collectstatic --noinput` gathers admin CSS/JS into `/app/staticfiles/` for Nginx to serve.
4. **Exec the CMD** — `exec "$@"` replaces the shell process with gunicorn, so gunicorn gets PID 1 and receives signals directly.

### 4.3 Docker Compose Architecture

Four services in `docker-compose.yml`:

```
                    ┌──────────┐
   Port 80 ────────►│  Nginx   │
                    └────┬─────┘
                         │ proxy_pass
              ┌──────────┼──────────┐
              ▼          ▼          ▼
         /static/    /api/      /admin/
         (served     (proxy     (proxy
          directly)   to        to
                      backend)  backend)
                         │
              ┌──────────┼──────────┐
              ▼                     ▼
          ┌─────────┐          ┌─────────┐
          │ Backend │─────────►│   DB    │
          │ :8000   │  (psql)  │  :5432  │
          └────┬────┘          └─────────┘
               │
               ▼
          ┌─────────┐
          │  Redis  │
          │  :6379  │
          └─────────┘
```

Key details:
- **`depends_on` with `condition: service_healthy`** — waits for the DB's `pg_isready` healthcheck to pass, not just for the container to start. Without this, the backend could start while Postgres is still initializing.
- **Named volumes** — `postgres_data` persists the database across container restarts. `static_files` is shared between backend and nginx for serving Django admin static files.
- **Environment injected via `environment:` block** — in a real production deployment, these would come from Docker secrets or a secrets manager, not plaintext in the compose file.

### 4.4 Nginx as Reverse Proxy

`nginx.conf` does three things:

1. **Reverse proxy `/api/` and `/admin/` to Django** — Nginx handles client connections, buffers requests/responses, and passes them to gunicorn. The `X-Forwarded-*` headers tell Django the original client IP and protocol.
2. **Serves frontend static files directly** — HTML, CSS, JS from `/usr/share/nginx/html`. The `try_files $uri $uri/ /index.html` enables SPA-style routing (any unmatched route falls back to `index.html`).
3. **Serves Django static files** — `/static/` maps to the shared `static_files` volume with 30-day cache headers. `Cache-Control: public, immutable` tells browsers "this file will never change, don't even revalidate."

**Why Nginx in front of Gunicorn?** Gunicorn is a WSGI application server, not a web server. It's not designed to handle slow clients, buffering, or static files efficiently. Nginx acts as a buffering reverse proxy — it absorbs slow client connections and passes clean requests to Gunicorn.

### 4.5 Environment & Secrets Management

The project uses `python-decouple` for environment variable management with a **layered fallback** pattern:

```python
SECRET_KEY = config('SECRET_KEY', default='django-insecure-...')
DEBUG = config('DEBUG', default=True, cast=bool)
```

- In development: defaults work out of the box (SQLite, debug mode, weak secret key)
- In production: all values come from environment variables set by Docker Compose or the deployment platform
- `cast=Csv()` parses comma-separated strings into Python lists
- `cast=bool` handles `'True'`/`'False'` string conversion

**Secrets never touch the codebase.** `.env.example` contains templates, not real values. The actual `.env` file is in `.gitignore`. In a cloud deployment (Render, Heroku, AWS ECS), these would be set via the platform's config vars/secrets manager.

### 4.6 Production Security Settings

`settings.py` reads 6 security-related environment variables:
- `SECURE_SSL_REDIRECT` — forces HTTPS
- `SESSION_COOKIE_SECURE` / `CSRF_COOKIE_SECURE` — cookies only over HTTPS
- `SECURE_HSTS_SECONDS` — HTTP Strict Transport Security
- `SECURE_HSTS_INCLUDE_SUBDOMAINS` — HSTS for subdomains
- `SECURE_COOKIE_ENABLED` — controls `Secure` and `SameSite=Strict` on auth cookies

All default to `False` for dev and are meant to be set to `True` in production. This is a clean pattern — security hardening is environment-controlled, not code-branch-controlled.

### 4.7 Database Strategy: SQLite → PostgreSQL

```python
DB_ENGINE = config('DB_ENGINE', default='django.db.backends.sqlite3')

if DB_ENGINE == 'django.db.backends.postgresql':
    DATABASES = { ... postgres config ... }
else:
    DATABASES = { ... sqlite config ... }
```

This **environment-driven database selection** lets the same codebase run SQLite locally and PostgreSQL in Docker/production with zero code changes — just set `DB_ENGINE` in the environment. The `psycopg2-binary` package is in `requirements.txt` so it's always installed; it just isn't used if SQLite is active.

### 4.8 CI Pipeline (GitHub Actions)

Referenced in the README badges. The CI workflow (`ci.yml`) likely runs:
- `pytest` with coverage (80% minimum threshold set in `pytest.ini`)
- `flake8` linting
- Docker build verification

The `pytest.ini` configuration:
```ini
addopts = --cov=. --cov-report=term-missing --cov-report=html --cov-fail-under=80 -v
testpaths = accounts transactions
```
- `--cov-fail-under=80` — the build fails if coverage drops below 80%
- `--cov-report=html` — generates an HTML report for human review
- `testpaths` limits test discovery to the two app directories

### 4.9 Health Check Architecture

`config/health.py` probes two dependencies:
1. **Database:** `connection.ensure_connection()` — executes `SELECT 1` or equivalent
2. **Cache:** Writes and reads back a test key — validates Redis is accepting commands

Returns 200 if both are healthy, 503 if either fails. This endpoint serves three purposes:
- Docker `HEALTHCHECK` instruction
- Load balancer health probes (if deployed behind one)
- Monitoring/alerting systems (ping every 30s, alert if 503)

### 4.10 WSGI/ASGI Entry Points

- `wsgi.py` — synchronous WSGI application, used by Gunicorn. `gunicorn config.wsgi:application --workers 3 --timeout 120`
- `asgi.py` — asynchronous ASGI application, available for future WebSocket support. Not used yet (the Dockerfile uses Gunicorn/WSGI).

The Gunicorn configuration: 3 workers (appropriate for a 2-vCPU container), 120-second timeout (handles long-running requests like summary computation on large datasets), and `--access-logfile -` sends access logs to stdout for Docker log aggregation.

## Interview Cheat Sheet: Common Questions & How to Answer

### "Explain the data model."
- Single custom model (`Transaction`) with UUID PK, Decimal for money, composite indexes
- Uses Django's built-in User model (profile pattern if extended)
- CASCADE deletion, user-scoped queries via `get_queryset()`

### "How does authentication work?"
- httpOnly cookie JWT, not localStorage — eliminates XSS token theft
- Custom `CookieJWTAuthentication` extends SimpleJWT with cookie extraction + Bearer header fallback
- Frontend auto-refresh on 401 via interceptor pattern
- Rate-limited login (5/min) for brute-force protection

### "What's the most complex query and how is it optimized?"
- `summary()` endpoint: 3 aggregation queries (SUM, COUNT, GROUP BY)
- Cached in Redis with 5-minute TTL, write-invalidated on CUD operations
- `select_related('user')` prevents N+1 on FK access
- Composite indexes on `(user, -date)`, `(user, status)`, `(user, category)` match query patterns

### "How would you scale this?"
- The architecture is already containerized and horizontally scalable
- Nginx reverse proxy can load-balance across multiple backend replicas
- PostgreSQL can be moved to a managed service (RDS)
- Redis cache reduces DB load; could add CDN for static assets
- Database indexes cover current query patterns; add query monitoring (Django Debug Toolbar in dev, APM in prod)
- Read replicas for reporting queries if summary becomes expensive at scale

### "What are the security measures?"
- httpOnly + Secure + SameSite cookie flags
- UUID PKs prevent enumeration
- CORS whitelist (not wildcard)
- Rate limiting on auth and general API
- Custom error handler avoids leaking stack traces
- Non-root Docker user
- Multi-stage build reduces attack surface
- All security settings environment-controlled (not hardcoded)

### "How would you test this?"
- pytest with `@pytest.mark.django_db` for database access
- `APIClient` with `force_authenticate` for authenticated requests
- Tests cover: CRUD, validation, user isolation, filter/pagination, summary calculations
- `conftest.py` disables throttling in tests
- 80% coverage floor enforced in CI
